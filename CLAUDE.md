## What this is

"Ondeck" — a job-application tracker (Kanban/table pipeline, analytics, CV builder, ATS scoring, manager dashboard). This is a from-scratch Next.js port of a Claude Design HTML prototype (`../Job Application Tracker - Google Auth.dc.html`, one level up from this app), rebuilt with a real backend rather than mocked client state. The prototype file is a useful reference for exact visual details (colors, copy, layout) but its internal structure (a single `x-dc` template file) should not be mirrored — this app uses ordinary Next.js conventions.

## Commands

```bash
npm run dev      # start dev server (Turbopack), http://localhost:3000
npm run build    # prisma generate && prisma migrate deploy && next build
npm run start    # run a production build
npm run lint      # eslint
npx tsc --noEmit  # typecheck (not in package.json scripts, run directly)
```

There is no test framework configured in this project.

`npm run build` runs Prisma migrations against `DATABASE_URL` as part of the build — this is what Vercel (or any CI) runs on every deploy, so schema changes just need a migration file committed (`npx prisma migrate dev --name <x>` locally), not a separate deploy step.

## Database (Prisma 7 — driver adapters, not the classic engine)

This project uses Prisma 7's driver-adapter architecture: `PrismaClient` **requires** an `adapter` in its constructor (see `src/lib/db.ts`), there is no bundled query-engine binary. The Postgres adapter is `@prisma/adapter-pg`. Config (`DATABASE_URL` resolution) lives in `prisma.config.ts`, imported via `dotenv/config` — `.env` is not auto-loaded by the Prisma CLI the way it was pre-v7.

The generated client lives at `src/generated/prisma` (not `node_modules/.prisma/client`), imported as `@/generated/prisma/client`. It's gitignored and regenerated by `postinstall` / `npm run build` — if you change `prisma/schema.prisma`, run `npx prisma generate` (or `migrate dev`) before the new fields/types are visible in TypeScript.

**Dev-server gotcha:** `src/lib/db.ts` caches the `PrismaClient` on `globalThis` (the standard Next.js-dev pattern to survive Fast Refresh without opening a new DB connection per edit). This means if you change the adapter, the schema's `datasource provider`, or `DATABASE_URL` while the dev server is running, Turbopack's hot reload will **not** pick it up — the cached client silently keeps talking to the old database/adapter. Fully kill (`pkill -f "next-server"` / `pkill -f "next dev"`) and restart the dev server after any change to `src/lib/db.ts`, `prisma/schema.prisma`'s datasource, or the DB connection string.

## Auth architecture

Session-cookie based, not JWT: `POST` to any `/api/auth/*` route sets/reads an opaque session id in an httpOnly cookie, looked up against the `Session` table (`src/lib/auth.ts`). Passwords are bcrypt-hashed. Google sign-in is verified **server-side** (`src/lib/google.ts`, via `google-auth-library`) against the Google ID token's signature and the client ID the request claims — never trust a client-decoded JWT for identity.

Admin/manager access is a `role` column on `User`, promoted only via the `ADMIN_EMAILS` env var (comma-separated emails), checked on every login/signup/Google auth in `syncAdminRole()` (`src/lib/auth.ts`). There is deliberately no client-supplied admin flag or password anywhere — `/app/manager` has its own `layout.tsx` that re-checks `role === "admin"` server-side (defense in depth beyond just hiding the nav link).

## Routing / data-flow structure

- `/` — unauthenticated onboarding + sign-in/sign-up wizard (`src/components/onboarding/`). Redirects to `/app` server-side if already authed (`src/app/page.tsx`).
- `/app/*` — the authenticated app, gated by `src/app/app/layout.tsx` (redirects to `/` if no session) which renders the shared sidebar/header shell (`src/components/app/AppShell*.tsx`) around each page's content.
- Each `/app/*` page is an async Server Component that fetches its own initial data server-side (mostly via `src/lib/app-data-server.ts`) and hands off to a client component for interactivity — avoids a loading-spinner flash on first paint. Client-side mutations (create/patch/delete) go through `/api/*` route handlers, never direct Prisma calls from client code.
- `src/components/providers/AuthProvider.tsx` and `ThemeProvider.tsx` are root-level client contexts (session user cache + `dark`/`light`/`mixed` theme, persisted to `localStorage`, applied via a `data-theme` attribute set before first paint in `src/app/layout.tsx` to avoid a flash).
- Shared derived-data logic (ATS scoring, kanban decoration, analytics aggregation — all ported from the prototype's `renderVals()`) lives in `src/lib/app-logic.ts` and `src/lib/ats.ts`, not duplicated per-component.

## Design tokens

All colors/fonts are CSS custom properties defined once in `src/app/globals.css` (`--bg`, `--surface`, `--accent`, `--st-*` pipeline-stage colors, `--font-ui`/`--font-display`/`--font-mono`, etc.) and consumed via inline `style={{ background: "var(--surface)", ... }}` throughout — this is the convention used everywhere in this codebase instead of Tailwind or CSS modules. The three themes only redefine these variables (see the `[data-theme="..."]` blocks); components should never hardcode a color. Fonts are loaded via `next/font/google` in `src/app/layout.tsx`, not the `<link>` tags the original prototype used.

## Known gaps (intentional, not bugs — read before "fixing")

- **No real email delivery.** Password-reset links are generated and stored for real (`PasswordResetToken`), but only ever logged to the server console (`src/app/api/auth/forgot-password/route.ts`) — no email provider is wired up.
- **File storage is Postgres-only and size-capped.** Application CVs, per-stage emails and home-assignment documents are real files (see "File storage" below). Onboarding's CV step and the CV Builder still only record a filename/tag string, not bytes.
- **LinkedIn sign-in is a UI-only placeholder** (shows an inert notice) — no LinkedIn OAuth app is wired up.
- **Billing is a UI-only mock.** `User.subscribed` / `billingPlan` / `trialStartedAt` exist and the trial-countdown math is real, but there's no Stripe (or other payment processor) integration — nothing actually charges anyone.
- **Manager Dashboard's usage/traffic numbers are static illustrative constants**, not real cross-tenant queries — intentional, since building real aggregate analytics across all users wasn't in scope and raises its own access-control questions.

## File storage

Uploaded files (a CV per application, emails attached to a stage, home-assignment brief/submission) live in the `StoredFile` table as `bytea` — no object-storage service. `src/lib/files.ts` owns the rules: 4 MB cap (under the ~4.5 MB serverless body limit), an extension allowlist (pdf, doc/docx, png/jpg/webp/gif, txt, eml, msg — never html/svg), and the stored MIME comes from the extension, not the client. Bytes are only ever served by `GET /api/files/[id]` (owner-checked; PDFs/images/text inline, everything else forced to download, `nosniff`). Upload with `POST /api/files` (multipart), then attach by id: `cvFileId` on `POST/PATCH /api/applications`, `/api/applications/[id]/emails` (file or pasted text, per stage), `/api/applications/[id]/assignment-files`. Those routes return the refreshed application. `deleteOrphanFiles()` removes a file once nothing references it — call it after detaching/deleting. Every application payload is built with `APP_INCLUDE` in `src/lib/serialize.ts`, so file metadata always rides along. On the client, `usePreview()` (`src/components/files/FilePreview.tsx`, mounted in `AppShellClient`) opens the shared viewer.

If you outgrow Postgres bytea (large files, many users), swap `saveUpload`/the `/api/files/[id]` handler for signed-URL object storage; the rest of the app only deals in file ids.

## Glass look & themes

`globals.css` defines translucent `--surface*` tokens over a `--glow` gradient, and one rule gives any element with an inline `background: var(--surface)` (or `--sb-bg`) the frosted `backdrop-filter` — so components stay plain inline-styled. Stage colours (`--st-*`) contain no purple by design. `mixed` overrides the sidebar tokens to stay dark/opaque (the translucent dark tokens go grey over the light glow).

## Env vars

- `DATABASE_URL` — Postgres connection string (required).
- `ADMIN_EMAILS` — comma-separated list of emails to auto-promote to `role: "admin"` on next login/signup (optional).
